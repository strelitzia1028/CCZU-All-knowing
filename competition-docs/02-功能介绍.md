# 功能介绍

本文档按用户端、内容端、互动端和管理端说明当前系统的完整功能。每个功能同时说明“具体设计”和“现实作用”，便于参赛展示和答辩。

## 1. 功能总览

| 一级模块 | 核心能力 | 主要对象 |
| --- | --- | --- |
| 校园 Agent | 需求理解、检索、草稿、修订、工具轨迹 | 所有登录用户 |
| 社区信息源 | 发布、筛选、搜索、讨论、私聊、有效期 | 所有登录用户 |
| 消息中心 | 公开互动与私聊提醒、未读状态、卡片展开 | 所有登录用户 |
| 知识库 | 知识维护、AI 分类、转存、搜索与筛选 | 管理员 |
| 审核后台 | 信息源审核、目录申请审核、用户监控 | 管理员 |
| 目录管理 | Tag 管理、信息源类型管理 | 管理员 |
| 账号系统 | 注册登录、角色权限、名称与密码维护 | 所有用户 |

## 2. 校园 Agent

### 2.1 自然语言需求理解

**设计**

- 对话可以携带最近 12 条本地历史。
- 后端先总结用户本轮需求，再结合历史补全“刚才、上一条、草稿”等指代。
- 规划器只输出任务计划，不直接回答用户。
- 规划结果会校验意图、标签、类型、关键词和时间范围。

**现实作用**

用户不需要学习复杂搜索语法。说“帮我找明晚打羽毛球的搭子”即可进入检索和草稿流程；说“刚才那个少一个人”可以进入草稿修订，而不是重新创建一个无关需求。

### 2.2 三种主要任务路线

| 路线 | 触发示例 | Agent 行为 |
| --- | --- | --- |
| 普通检索 | “学校有哪些运动场地？” | 检索知识库和社区信息源，基于结果回答 |
| 发布需求 | “明晚找两个人去图书馆学习” | 先检索，再准备待确认草稿 |
| 草稿修订 | “把刚才那个改成少一个人” | 找到上一份草稿，生成修订版本 |
| 普通问候 | “你好”“你能做什么？” | 简要介绍能力，不声称执行数据库操作 |

### 2.3 渐进式工具轨迹

**设计**

- 后端通过 SSE 流式返回 `agent_trace` 事件。
- 每一步都有工具名、中文标签、运行状态、摘要和耗时。
- 前端在生成过程中实时刷新“正在总结需求”“正在阈值检索”等提示。
- 工具结果先展示，回答正文再流式出现。

**现实作用**

用户能看见 Agent 为什么检索、检索了几轮、命中多少条，而不是面对一个不明所以的等待动画。对答辩展示而言，这也能直观证明系统不是普通问答页面。

### 2.4 匹配结果卡片

**设计**

- 知识库结果与社区信息源结果分别以卡片展示。
- 即使结果为 0，也会保留“知识库依据（0 条）”和“匹配到的社区信息源（0 条）”卡片。
- 社区卡片可点击展开完整内容。
- 卡片展示来源等级、匹配度、作者、时间、有效期和讨论状态。

**现实作用**

用户不仅能看答案，还能检查答案是否有依据。0 条结果也保持透明，避免把“没有检索到”误认为页面加载失败。

### 2.5 草稿生成与修订

**设计**

- Agent 只生成草稿，不自动发布。
- 草稿包含标题、正文、类型、Tag、地点和缺失目录申请。
- 用户需要先确认保存或提交审核。
- 修订时保留旧草稿中未被修改的内容，并特别处理“多/少几个人”等数量更正。

**现实作用**

既降低用户填写信息的成本，也保留用户对最终发布内容的控制权。修订能力避免每轮对话都新建一条重复信息。

### 2.6 无结果与异常兜底

- 检索最多进行三轮：全部 Tag、任一 Tag、仅关键词。
- 仍未达到阈值时，明确回复“无法找到匹配项，请减少限定词”。
- 如果是发布需求，可以在无检索结果时继续生成草稿。
- 模型规划或生成失败时，使用本地规则兜底，而不是让页面直接失效。

## 3. 社区信息源

### 3.1 发布与管理

**设计**

- 信息源包含标题、正文、类型、Tag、地点、联系方式和有效期。
- 新建后首先保存为草稿，再提交管理员审核。
- 用户只能编辑自己的草稿或驳回信息；已通过和审核中的内容不能由普通用户直接修改。
- 管理员可以修改或删除信息源。

**现实作用**

发布过程有明确状态边界，避免用户绕过审核修改已公开内容。草稿机制也让用户可以先保存再完善。

### 3.2 AI 自动选择 Tag 与类型

**设计**

- 输入标题后即可触发 AI 分析。
- 系统先总结内容，再结合 Tag 描述和类型描述进行语义匹配。
- 用户可打开或关闭“AI 自动添加”。
- 自动选择的 Tag 会高亮，内容变化后实时更新。
- 关闭自动 Tag 时会清空自动选择，避免用户误以为仍会自动变化。

**现实作用**

用户不必理解全部目录，也能发布到相对正确的分类中；自动结果仍可手动修改。

### 3.3 有效期与过期状态

**设计**

- 用户可填写“有效期至”，留空表示长期有效。
- 有效期不得早于或等于发布时间。
- 过期卡片显示红色“已过期”标签。
- 过期内容仍可被检索，但排序权重乘以 `0.65`。
- Agent 回答涉及过期内容时必须提醒用户核实。

**现实作用**

校园活动、交易和招募具有时效性。系统不直接删除过期内容，而是保留可追溯性，同时降低其优先级并提示风险。

### 3.4 时间、Tag、搜索和排序

**设计**

- 发布时间：今天、本周、本月、本年、所有。
- Tag 筛选支持多选和 OR/AND 模式。
- 搜索可勾选“匹配标题”“匹配内容”或两者。
- 排序支持按时间和按 Tag 匹配度。
- 默认按发布时间倒序展示。

**现实作用**

用户既能快速浏览最新信息，也能按活动类型、时间和标签精确定位。OR 适合扩大范围，AND 适合严格筛选子集。

### 3.5 公开讨论与私聊

**设计**

- 发布者可决定是否开放公开讨论。
- 开放后卡片显示绿色“可回复”标签。
- 所有信息源都支持仅双方可见的私聊。
- 消息显示发送者名称；管理员名称带蓝色“管理员”标签。
- 公开评论与私聊分开存储，第三方不能读取他人私聊线程。

**现实作用**

活动安排可以在公开讨论中同步，电话、具体集合点等隐私信息可以转移到私聊。

## 4. 消息中心

### 4.1 互动汇总

**设计**

- 汇总两类消息：自己信息源下的公开讨论，以及他人发给自己的私聊。
- 导航显示未读数量徽标，每 20 秒刷新。
- 支持全部/未读筛选、按标题/内容搜索、单条已读和全部已读。

**现实作用**

用户不需要逐个打开信息源寻找回复。新的互动会形成明确入口和提示。

### 4.2 消息卡片与继续回复

- 消息卡片展示发送者、时间、互动内容及对应信息源摘要。
- 点击后打开完整信息源卡片。
- 公开讨论进入公开回复区。
- 私聊消息直接定位到对应发送者的私聊线程。

**现实作用**

消息不是孤立通知，而是继续沟通的起点，减少从提醒到实际回复的操作步骤。

## 5. 知识库

### 5.1 知识维护

**设计**

- 管理员可新建、编辑、删除知识条目。
- 每条知识包含标题、正文、类型、来源等级和审核状态。
- 支持与信息源相同的 AI Tag/类型推荐逻辑。
- 历史知识可保留来源信息源关联。

**现实作用**

将稳定、可复用的校园事实沉淀为长期知识，减少用户重复提问和重复发布。

### 5.2 信息源转存知识库

**设计**

- 只有审核通过的信息源可转存。
- 同一条信息源通过唯一 `source_id` 约束只能转存一次。
- 转存后来源等级默认为“管理员审核”，并复制原 Tag。

**现实作用**

优质社区内容可以由管理员沉淀为长期知识，同时保持来源可追溯。

### 5.3 知识筛选

- 更新时间：今天、本周、本月、本年、所有。
- Tag 多选：OR/AND。
- 来源：官方、管理员审核、用户分享、全部来源。
- 搜索：可匹配标题、正文或两者。

## 6. 审核后台

### 6.1 信息源审核

**设计**

- 管理员逐条查看待审核信息源的内容、类型、作者、地点和 Tag。
- 支持通过或填写原因驳回。
- 审核动作写入审计日志。

**现实作用**

在内容公开前进行人工把关，降低虚假、重复和不当信息的传播风险。

### 6.2 Tag 与类型申请审核

**设计**

- Agent 或用户在现有目录无法覆盖时，只能提交申请。
- 申请进入待审核队列，不会自动成为正式目录项。
- 管理员分类审核通过后，才会创建或启用对应 Tag/类型。
- 已存在或重复待审的申请会被去重。

**现实作用**

目录随需求扩展，但不会被 AI 随意创建大量近义标签或无效类型。

### 6.3 用户监控

**设计**

- 展示所有用户，包括角色、创建时间、发布数、已通过数、公开讨论数和私聊发送数。
- 支持按显示名称/用户名搜索。
- 支持按名称和创建时间排序。
- 管理员名称在互动场景中显示蓝色标签。

**现实作用**

管理员可以观察账号活跃度和内容贡献，为后续社区治理提供依据。

## 7. Tag 与类型管理

### 7.1 Tag 管理

- 创建、编辑、启用、停用和永久删除 Tag。
- 停用后变灰且不再推荐，但仍保留历史关联。
- 支持按名称或创建时间排序。
- 支持搜索 Tag 名称与描述。

### 7.2 类型管理

- 类型有名称、唯一代码、描述和状态。
- 新建前二次确认代码，提醒“代码创建后不可修改”。
- 已被信息源使用的类型只能停用，不能永久删除。
- 支持按名称或创建时间排序。
- 支持搜索类型名称与描述。

**现实作用**

类型代码是数据库和数据交换的稳定标识，限制修改与删除可避免历史信息失配。

## 8. 账号与权限

### 8.1 注册与登录

- 普通用户使用用户名、显示名称和密码注册。
- 密码使用 `scrypt` 加盐哈希保存。
- 登录会话使用 HMAC 签名 Token。
- 管理员使用独立密码进入后台。

### 8.2 账号设置

- 登录用户可修改显示名称，名称大小写不敏感且全局唯一。
- 修改密码必须输入原密码、新密码和确认新密码。
- 服务端再次校验原密码、长度、两次新密码一致性和新旧密码差异。

**现实作用**

显示名称用于社区识别；密码修改流程避免仅凭登录态直接改密，降低账号被临时接管后的风险。

## 9. 体验与可靠性设计

- 页签切换采用淡出、模糊、淡入的轻量过渡。
- 卡片详情采用淡入淡出和模糊渐变，不使用突兀缩放。
- Agent 请求在切换选项卡后继续执行，返回问答页仍能看到结果。
- 对话按用户保存在浏览器本地，不占用服务端聊天存储。
- 回答卡片动画只在首次完成后播放，返回页面不会重复。
- 移动端与桌面端均支持筛选、卡片、弹窗和消息操作。

## 10. 状态流

### 信息源

`草稿 → 待审核 → 已通过 / 已驳回`

### Tag/类型申请

`待审核 → 已通过 / 已驳回`

### Agent 草稿

`待确认 → 已保存 → 已提交审核 → 已通过 / 已驳回 / 已删除 / 已放弃`
